# Keep the controller on Sonnet high

dforge's subagent-driven-development controller should stay on **Claude Sonnet 5.5 at effort `high`**. Opus 5.5 at `low` would cost more, not less. Opus charges exactly twice Sonnet's price on every meter. About 59% of the controller's bill is cache reads of a context that averages 217k tokens per call, so the repository's own paired data projects Opus `low` at about **1.4x the controller cost**, roughly +$4.3 and +10% per completed plan. Under subscription accounting, which Anthropic says tracks price, including cached context, that is the same increase in usage-limit burn. Opus `low` is also not the smarter option for this job. On every agentic benchmark that reports both settings, Opus `low` scores at or below Sonnet `high`. Anthropic recommends `low` for "simpler tasks… such as subagents" and never for a long agentic loop. Anthropic's own testing also shows that lowering effort cuts verification, which is the behaviour behind every recorded controller failure. The owner's framing ("model is how smart it is, effort is how careful it thinks") is half right. Effort also sets how many tool calls the model makes, how much it checks, and how much it does on its own initiative, and effort levels are calibrated separately for each model. So "smart model, low effort" is not a cheap way to get a smart model. If the controller ever needs more capability, the right step is Opus `medium` at about 1.9x cost, not Opus `low`. The cheapest real saving comes from fewer calls and a smaller re-read context, not from changing the model. The repository's planned Stage 1 production pilot edits and commits real plans, which breaks the owner's standing constraint. Any further measurement has to be a passive read of existing transcripts or a fully isolated replay.

## Effort sets how much work a turn does, not only how hard it thinks

Anthropic's definition of effort is wider than "how careful it thinks". The effort parameter "affects **all tokens** in the response", including text, tool calls and their arguments, and thinking. It works whether or not thinking is enabled, and "lower effort also means fewer and terser tool calls" ([Effort](https://platform.claude.com/docs/en/build-with-claude/effort)). Claude Code's documentation describes the behavioural effect more concretely. In Anthropic's tests on Opus 5.5, a higher level "tested more edge cases and verified more of its work before answering. It also made more choices on its own", while a lower level "returned a starting point sooner, which fits work where you review each result and steer the next step" ([Claude Code model configuration](https://code.claude.com/docs/en/model-config)). For Opus 5.5, adaptive thinking cannot be turned off, so effort is "the primary control for how much the model reasons and what a request costs" ([Effort](https://platform.claude.com/docs/en/build-with-claude/effort)).

The framing also assumes that effort level names mean the same thing on every model. They do not: "The effort scale is calibrated per model, so the same level name does not represent the same underlying value across models" ([Claude Code model configuration](https://code.claude.com/docs/en/model-config)). Sonnet 5.5's levels were recalibrated against Sonnet 5's ([Prompting Claude Sonnet 5.5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-sonnet-5-5)). Opus 5.5 thinks more per turn at a given level than Opus 5 did ([Prompting Claude Opus 5.5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-opus-5-5)). "Opus `low`" and "Sonnet `high`" can therefore only be compared by measurement. Anthropic's general advice points the same way: "Tuning effort is often a better lever than switching models" ([Choosing the right model](https://platform.claude.com/docs/en/about-claude/models/choosing-a-model)). Its recommended order is to sweep effort on the current model first, and only if that sweep shows a gap, to price the stronger model at low effort ([Optimizing for cost and intelligence](https://platform.claude.com/docs/en/about-claude/models/optimizing-for-cost-and-intelligence)).

A more accurate framing for this decision: **the model sets the ceiling on what the agent can work out, and effort sets how much work it does to reach it on each turn: how much it thinks, calls tools, checks, and acts unprompted.** This matters for a controller because its failures are failures to check (described below). Lowering effort reduces exactly that kind of work, whichever model runs.

Anthropic's per-model guidance follows the same logic. For Opus 5.5 it says to start at `medium`, the default, and sweep from there. It recommends `low` in one place only: integrations that previously ran Opus 5 with thinking disabled ([Prompting Claude Opus 5.5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-opus-5-5)). For Sonnet 5.5 in agentic coding and multistep tool use, it says to "start with `medium` for well-specified tasks and move to `high` for harder or longer ones" ([Effort](https://platform.claude.com/docs/en/build-with-claude/effort)). A multi-hour controller session is the "longer" case. Claude Code's own defaults are Opus 5.5 for Pro, Max, Team and API accounts, at `medium` effort for both Opus 5.5 and Sonnet 5.5 ([Claude Code model configuration](https://code.claude.com/docs/en/model-config)). No Anthropic document says Claude Code cloud sessions run Opus at `low`. The owner's observation that cloud "always use[s] opus low/medium" is most likely the account default, Opus `medium`, but that is inference. Either way, a cloud main loop does its own engineering work, whereas dforge's controller has had its judgment duties deliberately removed. Anthropic also publishes no guidance, and no measurement, for a lead or orchestrator agent at `low` effort on any 5.x model.

## Opus low trails Sonnet high on every agentic benchmark that reports both

Four data sets report both configurations, and each uses a different harness. On Anthropic's 478-problem SWE-bench Pro subset, the two tie: Opus `low` solved 87.4% and Sonnet `high` 87.6%, "inside run-to-run noise, for about 7% more per solved task". Opus `low` did this with "a little over half of Sonnet 5.5's output tokens and a little over a third of its cache reads". On Anthropic's internal agentic-coding benchmark (370 repository tasks graded by the repositories' own tests, run as a plain API agent loop), which is closer to a long tool-using session, **Sonnet `high` scored 77.8% at $0.33 per attempt against Opus `low`'s 74.8% at $0.35**. The Opus `low` arm there ran one attempt per task, against five for the other arms ([Optimizing for cost and intelligence](https://platform.claude.com/docs/en/about-claude/models/optimizing-for-cost-and-intelligence)).

The independent harnesses show a wider gap. Artificial Analysis lists each effort configuration as a separate model. It puts Sonnet `high` at **44% on Terminal-Bench 4.0 against 31% for Opus `low`**, and ahead on AutomationBench, GDPval and Briefcase. Opus `low` leads only on knowledge and long-context items such as HLE, SciCode and AA-LCR ([AA Sonnet high](https://artificialanalysis.ai/models/comparisons/claude-sonnet-5-5-high-vs-step-5); [AA Opus low](https://artificialanalysis.ai/models/comparisons/claude-opus-5-5-low-vs-step-5)). Artificial Analysis also leaves Opus `low` off its intelligence-versus-cost Pareto frontier, while Opus `medium` and above are on it ([AA article](https://artificialanalysis.ai/articles/claude-opus-5-5)). CursorBench 4.0 shows the same ordering. Those scores were measured in Cursor's own harness, with per-task costs taken from Anthropic's launch charts, and reached this report through a secondary source; its max-effort values match Anthropic's ([Apidog](https://apidog.com/blog/claude-sonnet-5-5-claude-code/); [Anthropic, Opus 5.5](https://www.anthropic.com/news/claude-opus-5-5)).

| Benchmark (harness) | Sonnet 5.5 medium | Sonnet 5.5 high | Opus 5.5 low | Opus 5.5 medium |
|---|---|---|---|---|
| SWE-bench Pro subset (Anthropic) | ~7 pts below high | 87.6% | 87.4% | 92.8% |
| Internal agentic coding (Anthropic, plain API loop) | 62.7%, $0.16 | 77.8%, $0.33 | 74.8%, $0.35 | 86.6%, $0.84 |
| Terminal-Bench 4.0 (Artificial Analysis) | 30% | 44% | 31% | 53% |
| AA Intelligence Index v4.3.2 | 41 | 47 | 42 | 51 |
| Output tokens per AA task | 21k | 37k | 10k | 26k |
| CursorBench 4.0 (Cursor harness) | 39.2%, $0.70 | 47.8%, $1.67 | 43.7%, $1.17 | 52.5%, $2.91 |

Harness differences matter here. On Terminal-Bench 4.0, Anthropic reports Sonnet 70.6% and Opus 66.4% at top effort, while Artificial Analysis measured 63.6% and 59.6% ([RITS summary of AA](https://rits.shanghai.nyu.edu/ai/claude-sonnet-5-5-ranks-2-at-56-behind-only-opus-5-5/)), so scores from different harnesses cannot share a column. The more important caveat is that **none of these benchmarks measures an orchestrator**: every one is a single-agent loop. Two findings come closer to the controller's situation. First, Opus `low` paired with a Fable advisor consulted the advisor on 1 of 300 tasks and scored about 7 points below Opus `low` alone ([Optimizing for cost and intelligence](https://platform.claude.com/docs/en/about-claude/models/optimizing-for-cost-and-intelligence)). Low effort suppressed the decision to escalate, and deciding when to escalate is a controller's job. Second, at the other extreme, Sonnet 5.5 at `max` spawned so many review subagents on FrontierCode that it scored below its own `xhigh` result ([Anthropic, Sonnet 5.5](https://www.anthropic.com/news/claude-sonnet-5-5)). Low effort risks the controller under-checking; very high effort risks it over-delegating. `high` sits between the two.

The one place the benchmarks do favour Opus is one level up. Opus `medium` beats Sonnet `high` on almost every metric above, at roughly 1.6x to 2.5x the cost depending on the harness. That is the real upgrade path, but its value depends on the controller needing judgment, and by design it does not.

## Opus doubles every meter, and the controller's bill is mostly cache reads

The price ratio is a flat 2:1. Opus 5.5 costs $4 input, $5 or $8 for a cache write (five-minute or one-hour), $0.20 for a cache read, and $20 output per million tokens. Sonnet 5.5 costs $2, $2.50 or $4, $0.10 and $10. Neither model has a long-context surcharge ([Anthropic pricing](https://platform.claude.com/docs/en/about-claude/pricing)). **Any mix of tokens therefore costs exactly twice as much on Opus**, and Opus `low` breaks even only if it uses half the price-weighted tokens Sonnet `high` uses. Effort reduces output directly, but cached input is re-read on every turn at a price set by the model, so effort reaches the cache bill only through fewer turns and slower context growth.

The repository has measured the controller's token profile. Across 15 completed plans run with a Sonnet 5.5 `high` controller, the median plan used **307 controller API calls, 66.1M cache-read tokens, 539k cache-write tokens and 202k output tokens, for $11.02**. That is 24.8% of Claude-side plan spend. By meter it splits into 59% cache reads, 19% output, and 22% cache writes plus input, with each request re-reading about 217k tokens of context ([controller-model-eval note](../../notes/2026-10-17-controller-model-eval.md)). The arithmetic for a switch is short. The only paired Opus-versus-Sonnet data is from implementer tasks, where Opus `low` took 19% fewer turns than Sonnet `high` at the same 9-of-10 pass rate ([tier-eval results](../../notes/2026-10-02-tier-eval-results.md)). If that turn reduction carried over to the controller, Opus `low`'s cache reads alone would come to about 53.5M tokens at $0.20, or **about $10.70, almost Sonnet's entire controller bill**, before any output or cache writes. Adding output at roughly half Sonnet's volume (about $2.00 at Opus prices) and the writes gives about $15 to $16. That matches the note's projection of about 1.4x, with a range of 1.2x to 1.6x. Applied to a $41.90 mean plan, that is +$4.30, or +10% ([controller-model-eval note](../../notes/2026-10-17-controller-model-eval.md)). The often-quoted Artificial Analysis figure, where Opus `low` costs about 0.51x Sonnet `high` per task ([Aivy, citing AA](https://aivy.com.au/resources/claude-sonnet-5-5-vs-opus-5-5/)), comes from short tasks dominated by output tokens. It is a lower bound that does not apply to a controller whose cost is mostly cache reads.

Subscription limits follow the same arithmetic. Anthropic says that on Pro, Max and Team plans the lower Opus 5.5 price "is passed on to your limits, including cached context" ([Claude blog](https://claude.dev/blog/what-a-task-costs-on-opus-5-5/)). That implies limits are charged at API-equivalent cost. The current help article lists a five-hour session limit, one weekly limit shared across models, and a separate weekly limit only for Fable ([Anthropic Help Center](https://support.claude.com/en/articles/11145838-using-claude-code-with-your-pro-or-max-plan)). An Opus controller therefore draws from the same weekly pool as Sonnet at twice the rate per token, and effort has no separate weight in limit accounting. Anthropic does not publish limit sizes or explicit model weights, so the 2x limit burn is an inference from the pricing statement, not a documented rule.

Cache lifetime has one implication for the controller. Claude Code caches for one hour on a subscription, but only five minutes on an API key, and also on a subscription once it is drawing on usage credits ([Claude blog](https://claude.dev/blog/what-a-task-costs-on-opus-5-5/)). The controller skill prescribes bounded waits of 5 to 10 minutes ([SKILL.md](../../../../plugins/dforge/skills/subagent-driven-development/SKILL.md)). By inference, every such wait outlasts a five-minute cache, so the next turn has to write the whole ~217k context again: about $1.09 on Opus or $0.54 on Sonnet at the five-minute write rate. Running the controller after the weekly limit has spilled over into usage credits costs far more than the plan-level figures above, on either model. Changing effort at the top level in the middle of a session also invalidates the cache ([Effort](https://platform.claude.com/docs/en/build-with-claude/effort)).

## The controller fails at diligence, not judgment

dforge built the controller as a coordinator with its judgment removed. The skill says: "Judgment belongs to the ruling seat, never to you, whatever model you run on." The controller reads the plan header and one task brief at a time. It runs scripts that print the next reviewer seat, writes the ledger, waits on background work, and carries out the ruling seat's verdicts word for word ([SKILL.md](../../../../plugins/dforge/skills/subagent-driven-development/SKILL.md)). The plan-writing rule states the consequence: "The controller owns no judgment calls — the ruling seat does — so it needs no stronger model" ([writing-plans SKILL.md](../../../../plugins/dforge/skills/writing-plans/SKILL.md)). What is left for the controller is a few classification calls: whether a NEEDS_CONTEXT question is mechanical, how to triage a BLOCKED report, whether to batch tasks, whether a review finding conflicts with the plan. The repository has no recorded case of the controller getting one of these wrong. The tier eval did find a large gap in judgment quality, with Opus `medium` catching 18 of 40 seeded defects against Sonnet `high`'s 10 ([tier-eval results](../../notes/2026-10-02-tier-eval-results.md)), but that was in the review seat, which the controller does not hold.

Every recorded controller failure is a failure to keep track of background work. A Sonnet 5 controller on darkcloud made 456 `sleep 1` calls and 293 `ListAgents` calls: 1,240 API calls and 707M cache-read tokens, about $84 of controller spend against $45 for all of that run's subagents. A Sonnet 5.5 controller stacked seven monitors and later admitted "That was sloppy". Another claimed "Nothing of mine is still running" while an agent and a shell were still running, and the owner had to send "check status" nudges in three more sessions. A keyword scan of 90 ledgers found no wrong dispatch and no skipped ledger line ([controller-model-eval note](../../notes/2026-10-17-controller-model-eval.md)). The note calls that weak evidence, because the controller writes its own ledger. Harness fixes landed on 2026-10-09 and 2026-10-10 (never hand off over work in flight; stopped work no longer counts as running), and a bounded-wait rule now forbids short-timeout polling.

These are lapses of checking, and checking is what Anthropic says effort controls. That cuts against Opus `low` specifically. Anthropic documents that Opus 5.5, at any effort level, "keeps the user updated as it works, and some of those updates end the turn with text rather than a tool call", which stops an unattended loop. Its advice is that if a background command or subagent is still running, the harness should not treat the task as done ([Prompting Claude Opus 5.5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-opus-5-5)). dforge has already hit this failure in its implementers and patched it with continuation messages. Pairing Opus with the lowest effort level risks the same failure in a controller whose rules require continuous execution. No Anthropic document says whether Opus `low` makes early stops more frequent. That remains unknown, but nothing in the documentation suggests `low` reduces them.

The two alternatives each carry their own risk. **Opus `medium`** is Anthropic's default for agent work and the strongest option on the benchmarks. It projects to about 1.9x controller cost, +$9.40 or +22% per plan, and it would buy judgment the controller's design does not use. **Sonnet `medium`** projects to about 0.8x, saving $1.80 or 4% per plan, and held pass rate on the repository's implementer rows 3 and 4 at 0.79x to 0.87x cost ([controller-model-eval note](../../notes/2026-10-17-controller-model-eval.md)). However, Anthropic documents that Sonnet 5.5 at `low` and `medium`, "on long agentic tasks, it's more likely to stop and check in with the user before it finishes" ([Prompting Claude Sonnet 5.5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-sonnet-5-5)). Sonnet `medium` also dropped 15 points on Anthropic's internal agentic benchmark and 14 on Terminal-Bench 4.0 (Artificial Analysis). A 4% plan-level saving does not justify that risk in the controller seat without isolated evidence.

## Measure only through existing transcripts and sealed replays

The recommendation is to **keep `claude --model sonnet --effort high` as the subagent-mode controller**. To spend less, reduce calls and context rather than buying a cheaper or smarter model. The controller re-reads about 217k tokens on each of roughly 300 calls per plan, and the single busy-wait incident cost more than every subagent in that run combined. Fewer calls per dispatch (currently 5.8), smaller resident context, earlier compaction, staying within the subscription's one-hour cache rather than usage credits, and keeping effort fixed for the whole session each address the 59% of the bill that a model swap can only double or leave as it is.

The existing Stage 1 pilot cannot run as written. Its README tells the operator, for each `opus@low` row, to "change the plan's `**Execution:**` line to `claude --model opus --effort low` and commit it before the first execution session", across the next six real subagent-mode plans ([evals/controller/README.md](../../../../evals/controller/README.md)). That is an edit to a real plan inside a real project, which the owner's standing constraint forbids. The harness's reading half is compliant: `measure.mjs` reads Claude Code transcripts and calls no model. Two measurements fit within the constraint. The first is a **passive read** of the 43 existing Sonnet 5.5 `high` controller sessions, splitting slip counts (in-flight launches, nudges, busy waits, seat misses) into sessions before and after the 2026-10-10 harness fixes. If tracking slips have stopped since the fixes, the only argument for Opus `low` is gone. The same read can firm up the per-call split between output and cache reads behind the break-even arithmetic. The second, needed only if slips persist, is a **fully isolated replay** of the deferred Stage 2. Register row 24 already lists its safeguards: no case that pushes, deploys, uses shared `/var/tmp` paths or runs proofs in an original repository's worktree; a temporary HOME; every case-by-arm cell filled before any decision; and costs summed across retries ([register](../../registers/2026-10-17-run-order-finish-controller.md)). Fixtures must be detached copies or synthetic plans, never worktrees of real projects. The arms should be Sonnet `high`, Opus `low` and Sonnet `medium`, plus Opus `medium` if Opus `low` shows slips that more effort might fix. The note estimates about $125 API-equivalent for the three-arm, three-case design, and with one repetition it only screens for large differences.

The conditions that would change this recommendation are specific. Move to Opus `low` only if an isolated replay shows it makes at least two fewer tracking failures than Sonnet `high` at no more than 1.5x per dispatch; that is the repository's existing rule, and a tie keeps Sonnet. Move to Opus `medium`, not `low`, if the controller takes on real judgment work, for example if the ruling seat is folded into it. Move to Sonnet `medium` if a replay matches Sonnet `high` case by case, with no early check-ins and under 20 busy-wait calls. Revisit the whole question if Anthropic narrows the 2:1 price ratio, gives Opus a separate weekly limit, or publishes effort guidance specific to orchestrators. Also revisit it if the controller's context shrinks enough that output rather than cache reads dominates its bill: in that regime Opus `low`'s much smaller output starts to count, as the 0.51x short-task figure shows.

The research turned up adjacent hazards worth recording. `next-step` correctly launches with `--effort`. If anything ever sets `CLAUDE_CODE_EFFORT_LEVEL` instead, that variable overrides every subagent's frontmatter effort, so every `judge-opus` and `impl-*` seat would silently run at the controller's level ([Subagents](https://code.claude.com/docs/en/sub-agents)). Switching the controller to `--model opus` would also move every inheriting subagent, such as Explore and general-purpose, onto Opus; dforge's named fleet agents carry explicit models. The `claude-api` skill's cached price table still lists Sonnet 5.5 cache reads at $0.20, against $0.10 live, which would halve Sonnet's apparent advantage in any calculation that uses it. The tier eval's 1.41x ratio comes from runs whose effort setting "could not be confirmed from the CLI output" ([tier-eval results](../../notes/2026-10-02-tier-eval-results.md)). Finally, the Opus 5.5 effort-sweep design note is untracked in git and still lists `judge-opus` at `high`, a setting that has since changed.

## Conclusion

The owner's framing makes Opus `low` look like a strong model running with less deliberation. Measured against benchmarks and Anthropic's own description of effort, it is a capable model doing less work per turn, at twice the price per token, in a seat where both the price and the reduced work count against it. A controller's value lies almost entirely in noticing what is still running, and noticing is the kind of work low effort cuts. The question that matters is therefore not which model is smarter. It is whether the 2026-10-10 harness fixes already closed the diligence gap. A passive read of existing transcripts can answer that at no cost and without touching a real project.

More broadly, for a long-lived orchestrator built on cached context, model choice works mostly as a multiplier on context size times call count, and effort works mostly as a setting for how carefully the agent checks. That makes dforge's largest lever for both tokens and usage limits the size of the context the controller re-reads around 300 times per plan, which neither of the configurations compared here changes.
