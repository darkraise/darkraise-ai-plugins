# Anthropic guidance on model and effort for an agentic controller (Opus 5.5 low vs Sonnet 5.5 high)

Retrieved 2026-10-18. Sources are Anthropic's own docs (platform.claude.com, code.claude.com, anthropic.com) unless marked secondary. Several fetches went through a summarizing fetch tool; quotes from the "Optimizing for cost and intelligence" reference list (lines starting "Claude Opus 5.5 alone...", "Compare models, work per task...") were read from the raw page text and are verbatim. Older models (Opus 4.x, Opus 5, Sonnet 5, Sonnet 4.6) are flagged as historical.

## What does effort control, what are the levels, and what are the defaults? (Includes a test of "model is how smart, effort is how careful it thinks")

### Takeaway
Anthropic defines effort as control over **all output tokens** (thinking, tool calls, and text), not only thinking depth: lower effort means less thinking, fewer and terser tool calls, less verification and less self-started initiative. The user's framing is half right: Anthropic does call effort "the main control for how much [the model] thinks", but it also says effort changes how many tool calls the model makes, how many edge cases it tests, how much it verifies, and how many choices it makes on its own, and that level names are not comparable across models. Defaults: Opus 5.5 = `medium`, Sonnet 5.5 = `high` on the API but `medium` in Claude Code.

### Cited Findings
- "The effort parameter lets you control how many tokens Claude spends when responding to requests. You can trade off between response thoroughness and token efficiency with a single model." — [Effort](https://platform.claude.com/docs/en/build-with-claude/effort)
- "The effort parameter affects **all tokens** in the response, including: Text responses and explanations; Tool calls and function arguments; Thinking (when active)... Because effort applies to every output token, it works whether or not thinking is enabled. Lower effort also means fewer and terser tool calls." — [Effort](https://platform.claude.com/docs/en/build-with-claude/effort)
- Effort with tool use: "Lower effort levels tend to: Combine multiple operations into fewer tool calls; Make fewer tool calls; Proceed directly to action without preamble; Use terse confirmation messages after completion. Higher effort levels may: Make more tool calls; Explain the plan before taking action; Provide detailed summaries of changes; Include more comprehensive code comments." — [Effort](https://platform.claude.com/docs/en/build-with-claude/effort)
- "Effort is a behavioral signal, not a strict token budget. At lower effort levels, Claude still thinks on sufficiently difficult problems, but thinks less than it would at higher effort levels for the same problem." — [Effort](https://platform.claude.com/docs/en/build-with-claude/effort)
- "At higher effort levels, Claude thinks more readily and at greater length. In a tool-use loop, follow-up requests that only process tool results can still skip thinking at any level. At lower levels, Claude can skip thinking entirely for simpler problems." — [Effort](https://platform.claude.com/docs/en/build-with-claude/effort)
- Level table (API docs): `max` "Absolute maximum capability with no constraints on token spending"; `xhigh` "Extended capability for long-horizon work... Long-running agentic and coding tasks (over 30 minutes) with token budgets in the millions"; `high` "Spends as many tokens as the task needs for excellent results... Complex reasoning, difficult coding problems, agentic tasks"; `medium` "Balanced approach with moderate token savings. The default on Claude Opus 5.5 and Claude Haiku 5.5... Agentic tasks that require a balance of speed, cost, and performance"; `low` "Most efficient. Significant token savings with some capability reduction... Simpler tasks that need the best speed and lowest costs, such as subagents". The page adds: "The per-model recommendations that follow override this table where they differ." — [Effort](https://platform.claude.com/docs/en/build-with-claude/effort)
- API defaults: "Most Claude models default to high effort... Claude Opus 5.5 and Claude Haiku 5.5 default to medium." Sonnet 5.5: "`high` is the default on the Claude API." — [Effort](https://platform.claude.com/docs/en/build-with-claude/effort)
- Claude Code defaults differ from the API for Sonnet 5.5: "The model's default effort: `high` on every model that supports effort, except that Opus 5.5, Sonnet 5.5, and Haiku 5.5 default to `medium`, Opus 4.7 defaults to `xhigh`..." — [Claude Code model configuration](https://code.claude.com/docs/en/model-config)
- Claude Code's own description of what effort changes: "In tests on Opus 5.5 and Fable 5.1, Claude at a higher level tested more edge cases and verified more of its work before answering. It also made more choices on its own. At a lower level, Claude returned a starting point sooner, which fits work where you review each result and steer the next step." — [Claude Code model configuration](https://code.claude.com/docs/en/model-config)
- "The effort scale is calibrated per model, so the same level name does not represent the same underlying value across models." — [Claude Code model configuration](https://code.claude.com/docs/en/model-config); same point for Opus 5.5: "Effort level names don't correspond to the same amount of thinking across models" — [Prompting Claude Opus 5.5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-opus-5-5)
- Opus 5.5: "Adaptive thinking is always on and can't be turned off, so effort is the primary control for how much the model reasons and what a request costs." — [Effort](https://platform.claude.com/docs/en/build-with-claude/effort)
- Opus 5.5: "At a given level, Claude Opus 5.5 tends to think more per turn than Claude Opus 5, especially at `xhigh` and `max`." and "To get less thinking, lower the effort level first. Lowering effort reduces thinking, and with it cost and latency, more reliably than prompt instructions do." — [Prompting Claude Opus 5.5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-opus-5-5)
- Sonnet 5.5: "Its levels are recalibrated: a level doesn't produce the same amount of thinking as the same level on Claude Sonnet 5." and "From `medium` up, the model thinks briefly before almost every reply, even a greeting... At `low`, it skips thinking on most simple requests." — [Prompting Claude Sonnet 5.5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-sonnet-5-5)
- Choosing-a-model page: "Tuning effort is often a better lever than switching models." — [Choosing the right model](https://platform.claude.com/docs/en/about-claude/models/choosing-a-model)
- Historical (Opus 5): "Effort controls thinking volume, not visible response length: on Claude Opus 5, changing effort does not reliably shorten responses" — [Effort](https://platform.claude.com/docs/en/build-with-claude/effort). Historical (Opus 4.7): "At lower effort levels, the model scopes its work to what was asked rather than doing more than requested. If you observe shallow reasoning on complex problems with Claude Opus 4.7, raise effort rather than prompting around it." — same page.
- Claude Code effort table: `low` "Quick exchanges where you review each result, such as brainstorming, a first sketch, or a small change like a rename"; `medium` "On Opus 5.5 and Sonnet 5.5, it fits day-to-day engineering work with a clear scope, such as implementing a new feature"; `high` "Work where verification matters or edge cases are likely, such as fixing a bug in an existing codebase"; `max` "may show diminishing returns and is prone to overthinking". — [Claude Code model configuration](https://code.claude.com/docs/en/model-config)

### Inferences
- "Model is how smart it is, effort is how careful it thinks" understates effort. In Anthropic's wording, effort sets how much *work* the model does per turn: thinking, number of tool calls, verification, edge-case testing and autonomy. For a controller whose job is mostly tool calls (reading ledgers, dispatching, waiting, routing), the tool-call and verification effects matter at least as much as thinking depth.
- Because levels are calibrated per model, "Opus low" vs "Sonnet high" cannot be reasoned about by level name; only measurements compare them (see next sections).
- The `--effort high` currently passed for Sonnet 5.5 in Claude Code is one level *above* Claude Code's Sonnet 5.5 default (`medium`), but equal to the API default.

### Gaps
- No Anthropic statement quantifies how effort changes tool-call counts for Opus 5.5 specifically (only the generic "fewer and terser tool calls" text and the token ratio in the next section).
- Not found: any statement on how effort changes waiting/polling behaviour on background work.

## How do Opus 5.5 and Sonnet 5.5 differ in capability and intended use? Does Anthropic compare Opus 5.5 at low effort with Sonnet 5.5 at high?

### Takeaway
Anthropic positions Opus 5.5 as the default starting point for most agentic work and Sonnet 5.5 as the speed/cost tier for everyday work, with "for the hardest long-horizon work, an Opus model is the better choice." Anthropic's own measurements put **Opus 5.5 at `low` roughly level with Sonnet 5.5 at `high`**: tied on a SWE-bench Pro subset (87.4% vs 87.6%, ~7% more per solved task for Opus), and **3 points behind** on Anthropic's internal agentic-coding benchmark (74.8% vs 77.8% at similar cost per attempt). Opus 5.5 at `low` does about half the output tokens and a third of the cache reads of Sonnet 5.5 at `high`. At their defaults, Opus 5.5 `medium` beats Sonnet 5.5 `high` by about 5 to 9 points for about 2 to 2.5 times the cost.

### Inferences
- On coding-style agentic work, Anthropic's data say Opus 5.5 `low` ≈ Sonnet 5.5 `high` in score and cost, so the swap is not an obvious win on capability alone; Anthropic's internal agentic benchmark (the closer analogue to a long tool-using loop) slightly favours Sonnet `high`. The difference (3 points, single run at Opus `low`) is small and possibly within noise; Anthropic does not state the noise band for that benchmark.
- Opus 5.5 `low` reaches its score with about half the output tokens. For a controller, fewer output tokens may mean fewer or terser tool calls, which cuts both ways (faster, but more risk of skipped reads or checks). This is inference from the "fewer and terser tool calls" text plus the token ratio.
- The step from Opus `low` to `medium` is large on every benchmark Anthropic reports (+5 to +14 points), larger than most other single-step changes. If the controller's decisions (routing, escalation) behave like the research/reasoning evals, `low` gives up more than it does on SWE-bench.
- None of these benchmarks measures an orchestrator that dispatches subagents; all are single-agent loops. Applying them to the dforge controller is extrapolation.

## Which effort levels does Anthropic recommend for agentic, tool-heavy and orchestration work, per model? What does it say about orchestrators vs subagents?

### Takeaway
For Opus 5.5 Anthropic says start at `medium` (its default) and sweep; it never recommends `low` for long agentic loops, describing `low` as for simpler tasks "such as subagents" and as close to Opus 5 `high` "on several coding evaluations". For Sonnet 5.5, agentic coding and multistep tool use start at `medium` for well-specified work and `high` for harder or longer work. Anthropic documents specific low-effort failure modes that matter for an unattended controller: Sonnet 5.5 at `low`/`medium` stops to check in early and at `low` skips verification; Opus 5.5 at any level may end a turn with a progress report. Anthropic's orchestrator guidance is to run the frontier model as the orchestrator and give workers the cheaper model, but its measurements found that a single model at lower effort often beat orchestration unless the work fans out or exceeds one context window.

### Inferences
- Anthropic's consistent pattern is "stronger model on the loop, cheaper model on workers", which favours Opus over Sonnet for a controller. Its effort guidance, however, never pairs that with `low`: `low` is described for subagents, simple tasks, and integrations that used to run without thinking.
- The controller's job (decide when to escalate, route reviews, wait on background work) is closer to an advisor-consult or escalation decision than to bulk coding. Anthropic's one data point on low effort in that role is negative: lowering effort collapsed the consult rate. That suggests Opus `low` might escalate or consult less often. This is inference by analogy, not a measured controller result.
- The early-stop behaviours are documented for Sonnet 5.5 at `low`/`medium` (not `high`) and for Opus 5.5 at all levels. Moving from Sonnet `high` to Opus `low` swaps one documented risk profile for another; Anthropic gives no Opus-5.5-specific statement that `low` makes early stops more frequent.
- The DRACO finding (Opus 5.5 lead rarely spawned helpers at `medium`) is a reminder that delegation frequency is itself effort- and prompt-dependent. dforge's controller dispatches by explicit procedure, so this may matter less, but it is unmeasured.

### Gaps
- Not found: Anthropic guidance or measurement for an orchestrator/lead agent at `low` effort on any 5.x model.
- Not found: a "Building effective agents" or Claude Code best-practices statement on lead-agent effort for the 5.5 family (the multi-agent research post is from 2025 and covers Opus 4 / Sonnet 4).
- Not found: whether Opus 5.5 at `low` skips verification or reads like Sonnet 5.5 and Haiku 5.5 do at `low`; Anthropic documents this for those two models only.

## How does Claude Code choose models and effort by default (CLI, cloud/web, subagents)?

### Takeaway
Claude Code's default model for Pro/Max/Team/Enterprise and the Anthropic API is Opus 5.5, and its default effort for Opus 5.5 and Sonnet 5.5 is `medium`. No document says cloud sessions (claude.ai/code) use a different model or effort, or that they run Opus at `low`. Subagents use the per-invocation model, then frontmatter `model`, then `CLAUDE_CODE_SUBAGENT_MODEL`, then the main conversation's model. Subagent effort comes from frontmatter or a per-invocation parameter, overriding the session level, but `CLAUDE_CODE_EFFORT_LEVEL` overrides both.

### Cited Findings
- "Pro, Max, Team, Enterprise, and Anthropic API: defaults to Opus 5.5; Claude Platform on AWS, Amazon Bedrock, and Google Cloud's Agent Platform: defaults to Opus 5.5; Microsoft Foundry: defaults to Sonnet 4.5"; "Fable models are not the account-type default on any plan or provider." — [Claude Code model configuration](https://code.claude.com/docs/en/model-config)
- Aliases on the Anthropic API: `opus` → Opus 5.5 (v2.1.280), `sonnet` → Sonnet 5.5 (v2.1.284), `haiku` → Haiku 5.5 (v2.1.293); `sonnet` "Uses the latest Sonnet model for daily coding tasks", `opus` "Uses the latest Opus model for complex reasoning tasks"; `opusplan` uses opus in plan mode and sonnet for execution. — [Claude Code model configuration](https://code.claude.com/docs/en/model-config)
- Effort resolution order: "1. An explicit choice: the `CLAUDE_CODE_EFFORT_LEVEL` environment variable, launching with `--effort`, or `/effort` in the session; 2. Your settings: the level you saved for the model or an `effortLevel` key...; 3. The model's default effort..." and "Opus 5.5 starts at `medium` unless one of the sources above sets a level for it, and a top-level `effortLevel` in your user settings file doesn't count for Opus 5.5." — [Claude Code model configuration](https://code.claude.com/docs/en/model-config)
- "Opus 5.5 defaults to `medium`, one level below Opus 5's default of `high`. In Anthropic's testing, Opus 5.5 at `medium` matches or exceeds Opus 5 at `high` on coding and knowledge-work evaluations... start at `medium` rather than carrying over the level you used on Opus 5." — [Claude Code model configuration](https://code.claude.com/docs/en/model-config)
- Ultracode: "a Claude Code setting rather than a model effort level: with it on, Claude orchestrates dynamic workflows for substantive tasks, at whichever effort level the session runs at." `--effort ultracode` also sets the level to `xhigh`. — [Claude Code model configuration](https://code.claude.com/docs/en/model-config)
- Cloud sessions: `/model` and `/effort` "pass the value as an argument, for example `/model sonnet`, instead of opening the terminal picker or slider"; settings come from environment variables on the cloud environment or the repo's committed `.claude/settings.json`. No default model or effort for cloud sessions is stated. — [Use Claude Code in the cloud](https://code.claude.com/docs/en/claude-code-on-the-web); "settings deployed to your device do not reach them" — [model-config](https://code.claude.com/docs/en/model-config)
- Subagent model order: "1. The per-invocation `model` parameter; 2. The subagent definition's `model` frontmatter, where `inherit` selects the main conversation's model; 3. The `CLAUDE_CODE_SUBAGENT_MODEL` environment variable...; 4. The main conversation's model". — [Subagents](https://code.claude.com/docs/en/sub-agents)
- "If you switch models with `/model`, the switch also reaches subagents that inherit the main conversation's model... To keep a custom subagent on a smaller model, set `model` in its definition." — [Claude Code model configuration](https://code.claude.com/docs/en/model-config)
- Built-ins: Explore uses "the main conversation's model" (Opus when the main model is Fable on first-party connections); Plan "inherits from the main conversation"; general-purpose uses `CLAUDE_CODE_SUBAGENT_MODEL` if set, otherwise the main model; claude-code-guide uses Haiku; statusline-setup uses Sonnet. — [Subagents](https://code.claude.com/docs/en/sub-agents)
- Subagent effort: frontmatter `effort` "Overrides the session effort level, but not the `CLAUDE_CODE_EFFORT_LEVEL` environment variable"; a per-invocation `effort` parameter (v2.1.292+) "overrides the `effort` field... The `CLAUDE_CODE_EFFORT_LEVEL` environment variable takes precedence over both." — [Subagents](https://code.claude.com/docs/en/sub-agents)
- Subagents inherit thinking on/off from the main session (v2.1.198+); "There is no per-subagent thinking setting." — [Subagents](https://code.claude.com/docs/en/sub-agents)
- Per-message effort changes keep the prompt cache; a top-level effort change "invalidates the prompt cache" — [Effort](https://platform.claude.com/docs/en/build-with-claude/effort)

### Inferences
- Out-of-the-box Claude Code on a subscription already runs the main loop as Opus 5.5 at `medium`, so Anthropic's own product default sits between the two dforge options (Opus, but one level above `low`).
- Switching the controller from `--model sonnet` to `--model opus` changes the model of every subagent that inherits (built-in Explore, Plan, general-purpose, `claude`, forks, and any definition with `model: inherit`). dforge's `impl-*`, `judge-*` and `scout-*` agents carry explicit models in their names and descriptions, so they should be unaffected, but this was not checked against their frontmatter.
- Adjacent hazard: if dforge ever sets the controller's effort through `CLAUDE_CODE_EFFORT_LEVEL` rather than `--effort`, that variable overrides every subagent's frontmatter `effort`, so all `impl-opus-high` / `judge-opus` seats would silently run at the controller's level. `--effort` does not have this effect.
